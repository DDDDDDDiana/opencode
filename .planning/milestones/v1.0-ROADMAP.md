## Phases

### Phase 1: Identity Foundation

**Goal**: Users can authenticate with API keys and their identity propagates through the request pipeline
**Depends on**: Nothing (first phase)
**Requirements**: AUTH-01, AUTH-02, AUTH-03, AUTH-04
**Plans**: 4 plans

Plans:

- [x] 1.1 Minimal identity persistence and API key primitives
- [x] 1.2 UserContext ALS and identity helpers
- [x] 1.3 Global auth middleware and structured logging
- [x] 1.4 Migration, verification, and regression coverage

**Details:**

1. A request with a valid `x-opencode-api-key` header is accepted and the user identity is available throughout the request.
2. A request with an invalid or missing API key falls back to anonymous mode without error.
3. API keys are never stored in plaintext; only hashes exist in the database.
4. `UserContext` is accessible via ALS anywhere in the call stack.

### Phase 2: Session Ownership

**Goal**: Every session belongs to a user and cross-user data access is impossible
**Depends on**: Phase 1
**Requirements**: SESS-01, SESS-02, SESS-03, SESS-04, SESS-05, SESS-06
**Plans**: 6 plans

Plans:

- [x] 02-01 Add `user_id` column to SessionTable, filter create() and list()
- [x] 02-02 Ownership checks in get(), remove(), and fork()
- [x] 02-03 Ownership filtering in listGlobal() and children()
- [x] 02-04 Generate Drizzle migration and full typecheck
- [x] 02-05 Propagate remove() ownership errors
- [x] 02-06 Restore end-to-end ownership enforcement after audit gaps

**Details:**

1. User A cannot list, read, fork, or delete sessions belonging to User B.
2. New sessions created by an authenticated user are automatically tagged with that user's id.
3. Forked sessions inherit the parent session's owner, not the requesting user.
4. Anonymous requests see only sessions with no owner (`user_id IS NULL`).
5. Existing deployments with no API key configured continue to work without migration.

### Phase 3: User Management API

**Goal**: Admins can create and manage users, issue API keys, and inspect usage
**Depends on**: Phase 1
**Requirements**: USER-01, USER-02, USER-03, USER-04, USER-05, USER-06
**Plans**: 5 plans

Plans:

- [x] 03-01 Extend UserTable schema + User.create() and User.get()
- [x] 03-02 User.update() quota patching + User.remove() with session orphaning
- [x] 03-03 UsageTable schema + Usage.record() and Usage.stats()
- [x] 03-04 HTTP routes (POST/GET/PATCH/DELETE /user, GET /user/:id/usage)
- [x] 03-05 Typecheck cleanup for user auth and bcrypt types

**Details:**

1. Admin can create a user and receive a plaintext API key exactly once; subsequent reads never expose it.
2. Admin can update a user's quota settings via PATCH and changes take effect on the next request.
3. Admin can delete a user; their sessions are orphaned (`user_id` set to `NULL`), not deleted.
4. Admin can retrieve per-user token consumption stats aggregated by date.

### Phase 4: Resource Protection

**Goal**: Users cannot exceed their allocated resources and can only access permitted models
**Depends on**: Phase 2, Phase 3
**Requirements**: QUOTA-01, QUOTA-02, QUOTA-03, QUOTA-04, MODEL-01, MODEL-02, MODEL-03, USAGE-01, USAGE-02, USAGE-03, USAGE-04
**Plans**: 5 plans

Plans:

- [x] 04-01 Record token usage in `processor.ts` finish-step
- [x] 04-02 Define `QuotaError` and `ModelAccessError` contracts
- [x] 04-03 Concurrent session + daily token quota enforcement
- [x] 04-04 Agent call quota in prompt loop
- [x] 04-05 Model allowlist check in `Provider.getModel()`

**Details:**

1. A user who has exhausted their agent call quota receives a clear error and the request is rejected.
2. A user cannot open more concurrent sessions than their limit allows.
3. A user who has hit their daily token cap cannot start new LLM calls until the cap resets.
4. A user attempting to use a model not on their allowlist receives an error listing the permitted models.
5. Token consumption is recorded per session after each LLM call completes and is visible via the usage API.

## Milestone Summary

**Key Decisions:**

- API key auth instead of JWT for service-mode simplicity and lower integration cost
- `UserContext` implemented parallel to `Instance` rather than extending it
- `user_id` left nullable on sessions for backward compatibility and anonymous fallback
- Quotas fail closed with explicit errors instead of silent downgrade behavior
- Milestone shipped after audit review with remaining gaps tracked as accepted tech debt

**Issues Resolved:**

- Added API-key-backed identity propagation throughout the request pipeline
- Restored missing session ownership enforcement after a late audit catch
- Completed user and usage APIs with clean typecheck coverage

**Issues Deferred:**

- Message and part routes still need session ownership enforcement (`SESS-03`)
- Deleted user ids still expose `/user/:id/usage` stats (`USER-05`, `USER-06`, `USAGE-04`)
- Nyquist validation artifacts were not produced during this milestone

**Technical Debt Incurred:**

- Audit gaps were accepted to keep `v1.0` on schedule
- Validation evidence remains incomplete until `*-VALIDATION.md` files are generated
